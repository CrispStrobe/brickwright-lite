# A portable IR tower, as a contract

The RCX is reachable only through an infrared tower. LEGO's own towers —
serial (`9709`) and USB (`0694:0001`) — are two decades out of production, and
a host with neither cannot talk to a brick at all. A tower is, however, a very
small device: a 38 kHz carrier, one LED, one demodulator, and a level-shifted
serial line.

`maehw/DiyIrTower` demonstrates exactly that, on an ATtiny13A. Its README
names the parts and the compatible hosts (WebPBrick, Bricx Command Center,
`firmdl3`), and states that other 8-bit AVRs such as the ATtiny85 may work
"with timing adjustments".

That last clause is the whole motivation for this file. We want a tower that
is *portable by construction* rather than by adjustment — one that builds for
an RP2040, an ESP32, an STM32, an ATtiny85, or an Arduino, because the parts
people actually have on a desk are not ATtiny13As.

## The licensing position

`maehw/DiyIrTower` is **GPL-3.0** (`LICENSE`). Its firmware therefore cannot
be the basis of something we publish under our own terms, and the port we want
is a re-architecture in any case.

So this is the same clean-room arrangement as
[`docs/RCX-IR-PROTOCOL.md`](./RCX-IR-PROTOCOL.md), and it is worth restating
because the roles only work if they are kept:

  * **Specifier** — writes this file. May read anything. Writes no code.
  * **Implementer** — **must not read `maehw/DiyIrTower`, at all**, nor any
    other GPL tower firmware. Works from this file, from RCX Internals, and
    from component datasheets.
  * **Auditor** — the specifier, reviewing the result against this contract.

The facts below are all either physics, datasheet, or Kekoa Proudfoot's *RCX
Internals* (1998). None of them is DiyIrTower's to own. What is theirs is the
expression — their file layout, their register writes, their naming — and we
take none of it. As written, this file is not a description of their firmware;
it is a description of the problem.

Their project remains useful in the way that costs nothing: as an **oracle**
and as a hardware reference. If our tower does not work and theirs does on the
same board, theirs is the one that has met a real brick.

## What the device has to do

Two independent, simultaneous, unidirectional paths. That is the entire
functional specification.

### Transmit: host → brick

From RCX Internals (quoted in full in the protocol contract):

> "The infrared signal is generated by inverting the serial data and
> modulating it with a 38 kHz carrier. Serial zeros generate light, while
> serial ones do not."

So the transmit path is:

```
IR LED drive = carrier(38 kHz) AND NOT(host TXD)
```

and nothing else. Read that as narrowly as it is written — it is the single
most important design decision available here:

**The tower does not decode serial. It gates a carrier.**

A gating tower has no baud rate, no parity setting, no framing, and no state.
It therefore works unchanged at 2400 baud 8-O-1 (normal operation) *and* at
the 4800/no-parity mode `firmdl3` uses for firmware download, and at anything
else anyone invents later. A decoding tower has to be told, and gets it wrong.
This is also why the port is easy: a gate needs one timer and two pins, which
every MCU on the list has, whereas a bit-banged UART needs cycle counting,
which is what "timing adjustments" means.

### Receive: brick → host

The demodulator does the work. A 38 kHz receiver module (Vishay TSOP series)
outputs a *demodulated* logic level: idle high, low while a burst is present.
Since a burst is a serial zero and idle is a serial one, its output is already
TTL serial of the correct polarity, and the receive path is:

```
host RXD = receiver output
```

possibly straight through in hardware. **The implementer must verify this
polarity claim against the datasheet of the part actually used** rather than
take it from here; getting it backwards produces a line that frames every byte
as garbage, silently.

### What it must not do

  * It must not suppress the echo. Infrared is a broadcast medium and the
    tower hears its own LED; the *host* discards the echo, and our protocol
    module already does (it matches `~opcode` replies). A tower that tried to
    gate its own receiver during transmit would have to know when transmission
    ends, i.e. would have to decode, which is exactly what we are avoiding.
  * It must not buffer. There is nothing to buffer: the gate is combinational.
  * It must not implement any part of the RCX protocol. The tower has never
    heard of an opcode.

## The facts a port needs

### The carrier

38 kHz, nominal. Generate it from a hardware timer, never from a delay loop:

```
divisor = F_CPU / (2 * 38000)      /* for a toggle-on-compare timer */
```

State the achieved frequency, not the intended one. The receiver's passband is
narrow — its sensitivity falls off within a few kHz of centre — so a port
whose timer cannot land close to 38 kHz is a port that half-works at short
range, which is the most expensive kind of bug to diagnose. **Each supported
board must record its achieved carrier frequency and the error in percent**,
computed from its real clock, as a build-time constant that a test can assert.

Duty cycle: the datasheets specify 50 % for the passband figures; lower duty
trades range for LED current. Make it a parameter with 50 % as the default.

### The receiver module, and the one trap in it

At 2400 baud a bit is 1/2400 = 416.7 µs, which is 15.8 carrier cycles. The
longest possible run of serial zeros is a start bit followed by eight zero
data bits — nine bits, 3.75 ms, about **142 carrier cycles of continuous
burst**.

That number matters because IR receiver modules are designed for remote
controls, and many of them deliberately **suppress long continuous bursts** as
if they were interference: automatic gain control pulls the output back to
idle mid-byte. A module chosen for noise immunity is often precisely the wrong
one for data.

DiyIrTower's README names the **TSOP4338** and **TSOP4838** as suitable. The
Vishay families differ in exactly this AGC behaviour, and the specifier did
not establish with confidence which of the two tolerates the longer burst.
So this is an explicit verification item, not a fact:

> **Verify from the datasheet** that the chosen receiver permits a continuous
> burst of at least 142 cycles (≥ 4 ms at 38 kHz) without AGC suppression, and
> record the part number and the datasheet figure alongside the driver. If the
> datasheet is ambiguous, this is testable directly: send `0x00` repeatedly
> and check that every byte arrives.

### The LED

940 nm, driven through a current-limiting resistor. Peak current sets range;
the pulsed duty means the average is well under the DC rating, but the
contract here is only that **the drive strength is a parameter of the board,
not a constant in the driver**, since an RP2040 pin sources a different
current from an ATtiny pin and some boards will want a transistor.

### Serial levels

TTL, not RS-232. A USB-serial cable at 3.3 V or 5 V connects directly; a true
RS-232 port needs a level shifter and inverts, which is a board concern and
must not leak into the driver.

### The USB identity, if a board presents one natively

A board with native USB (RP2040, ESP32-S3, STM32) can be its own serial
adapter and appear directly as a port, removing the cable. If it does, it
should present itself as an ordinary CDC-ACM device under its own VID/PID —
**not** as `0694:0001`. That pair belongs to LEGO's USB tower; claiming it
would be identity theft of a device whose driver protocol we do not implement,
and our own WebUSB filter is ours to choose.

## The shape we want

One portable driver, one thin port layer per board. The port layer is the only
thing a new board has to write, and it should be small enough to read in a
sitting:

```
  carrier_init(frequency_hz, duty) -> achieved_hz
  carrier_on()  / carrier_off()      /* gate, not start/stop */
  tx_pin_read() -> bool              /* host TXD */
  rx_pin_write(bool)                 /* host RXD, if not wired through */
```

Whether the gate is done in software (poll `tx_pin_read`, call
`carrier_on/off`) or in hardware (the timer output is ANDed with the input pin
by the peripheral itself, costing zero CPU) is a per-port choice, and the
driver must permit both. On parts where the timer can be gated by a pin, the
firmware does nothing at all at runtime, which is the ideal.

**Latency budget**: the software-gated path must decide within a small
fraction of a bit time. At 2400 baud that is 416.7 µs, so a polling loop
sampling at, say, 20 kHz is comfortable; state the sampling rate and the
resulting worst-case edge jitter for each port, and assert it.

## Build order

1. **The carrier**, alone, on one board. Measurable with a scope or a second
   MCU: assert the achieved frequency and duty against the spec above. No RCX
   needed.
2. **The gate**: feed a known serial pattern in, confirm the LED drive is its
   inverse ANDed with the carrier. Still no RCX.
3. **Loopback through a receiver module**: LED to receiver across a desk,
   host TXD to host RXD through the pair. Every byte sent must come back
   byte-identical. This is where the AGC trap above appears, and it appears
   without a brick.
4. **A real brick**: `ALIVE` (`0x10`) and read the reply. Our protocol module
   in `overlay/scratch-gui/src/lib/rcx/rcx-protocol.js` already encodes it, so
   this step needs no new host code.
5. **A second board**, from the port layer only. If step 5 needs a change
   anywhere but the port layer, the abstraction in the section above is wrong
   and should be fixed rather than worked around.

Steps 1–3 need no LEGO hardware whatsoever, and are where the mistakes live.

## What "done" looks like

  * Two boards supported, neither of them privileged in the source.
  * A host can drive it with the existing protocol module and nothing else.
  * The achieved carrier frequency and the receiver's burst tolerance are
    recorded numbers, per board, not assumptions.
  * No file in the result is a translation of anything.
