## Recommendation

Use the LabWired engine that Lite already ships. Its ESP32-S3 path boots
the retained Rust and Arduino-compatible flash images through the implemented
loader candidate. Adopt that qualified supplier path first, then qualify and
release the new 4848S040 RGB and GT911 model candidates upstream. Give
code generation, compilation, hardware upload, and emulation separate capability
states and acceptance tests.

The target is two layers:

- `esp32s3`: the existing Xtensa LX7 chip identity, with explicit memory and boot
  configuration. An S3 is not an ESP32-C3/RISC-V target or an ESP8266/LX106 target.
- `esp32_4848s040`: the new board identity for the common GUITION
  ESP32-4848S040C_I assembly: S3-WROOM-1, 16 MB flash, 8 MB octal PSRAM,
  ST7701 480 x 480 RGB LCD and GT911 capacitive touch. Exact relay/audio variants
  and panel timings are board configuration, not chip identity.

## What exists and where it stops

### The S3 engine already has substantial functionality

The shipped `labwired-core/crates/wasm/src/lib.rs` dispatches the S3 to a
chip-specific implementation. `new_from_config_xtensa_esp32s3_flash` starts
from the real ROM reset vector using merged flash, flash-MMU mappings and
both application CPUs. The SoC implementation includes an 8 MiB octal PSRAM
model, flash sizing from the chip descriptor, floating-point execution,
GPIO/peripheral routing and external-device attachment.

The old `labwired-core/docs/boards/esp32s3.md` contains superseded statements
about missing FPU/PSRAM and older boot behavior. Source inspection and the
executed checks above are the evidence for this proposal.

### Lite already discovers the chip

`debug-panel.jsx::ensureLabwiredChips()` reads `bw-board/labwired-catalog.js`.
That catalog contains `esp32s3` and an `esp32s3-oled-demo` board. The latter
is an SSD1306 OLED example, not the 4848S040.

The general firmware-only factory supports addressed ELF and Cortex-M UF2,
and exposes registers, memory, stepping, breakpoints and serial. The qualified
S3 paths here use addressed Xtensa ELF or the explicit merged-flash mode.
Firmware-only mode has no circuit attached. Its raw-binary guard is appropriate for a generic chip:
an unaddressed file cannot safely be placed at a guessed address.

The new M1 candidate adds a distinct explicit merged-flash route. Its named
ROM/flash inputs and reset-time reconstruction use the validated upstream boot
profile; the generic raw-binary guard remains intact.

### A classic-ESP32 integration defect is relevant but separate

`labwiredAdapterOptionsFor()` returns `arduinoEsp32` for the classic DevKit
profile, but `debug-target-factory.js` drops that field before creating its
adapter. The existing classic LEDC test constructs the adapter directly and
therefore does not cover that loss. This is a source-observed classic-ESP32
defect, not a measured S3 failure. Do not fix S3 by enabling classic-ESP32
quirks for every Xtensa target; the demonstrated S3 ROM-boot path needs none.

### The RGB board is the substantial emulator addition

The shipped S3 `lcd_cam.rs` implements configuration, completion interrupts
and i80/GDMA pixel transfers. It explicitly lacks RGB sync generation and
pixel/line/frame timing. Existing i80 panel support cannot drive this board
unchanged. No ST7701 or GT911 model was found in the inspected core.

The ST7701 interface uses 3-wire SPI for commands and parallel RGB for pixels.
A production model must join both paths. A canvas that bypasses the guest's
LCD_CAM/GDMA configuration would be an API-level preview with different
compatibility guarantees.

## Board profile

Initial configuration: common display/touch assembly, optional relay/audio
hardware represented as explicit variants. Manufacturer specs establish the
memory sizes and panel identity; Arduino_GFX supplies a concrete pin profile.

| Function | GPIO assignment |
| --- | --- |
| LCD configuration CS / SCK / MOSI | 39 / 48 / 47 |
| RGB DE / VSYNC / HSYNC / PCLK | 18 / 17 / 16 / 21 |
| Red bits, low to high | 11, 12, 13, 14, 0 |
| Green bits, low to high | 8, 20, 3, 46, 9, 10 |
| Blue bits, low to high | 4, 5, 6, 7, 15 |
| Backlight | 38 |
| GT911 SDA / SCL | 19 / 45 |
| Touch address | Default `0x5d`; retain explicit alternative-address configuration |

For a flat RGB565 D0..D15 array, the derived order is:

```text
4, 5, 6, 7, 15, 8, 20, 3, 46, 9, 10, 11, 12, 13, 14, 0
```

Arduino_GFX's `ESP32_4848S040_86BOX_GUITION` preset uses 12 MHz pixel clock,
H front/pulse/back 10/8/50, V front/pulse/back 10/8/20 and the type-9
ST7701 initialization sequence. The ESPHome board recipe uses different back
porches. Store a named, sourced timing preset and allow overrides; one timing
tuple is not established for every panel revision.

One RGB565 frame is `480 * 480 * 2 = 460800` bytes; two frames require
921600 bytes. PSRAM-backed buffers, strides, descriptor chaining and frame
boundaries are consequently part of the firmware contract.

GPIO19 and GPIO20 are the S3's native USB pins, but this board uses them for
touch SDA and LCD data. The initial hardware upload profile should use its
actual UART bridge, with USB-CDC-on-boot disabled for board firmware. Do not
infer a native-USB debugger connection from the USB connector alone. Generic
S3 boards may have separate USB-capable profiles.

S3 GPIO22..25 do not exist. Reserve the memory bus pins, including GPIO33..37
when octal PSRAM uses them, and distinguish boot strapping from runtime pin
functions. Board pin availability is narrower than the chip's GPIO range.
The inspected touch recipe polls GT911 without named reset/interrupt pins;
do not invent those physical connections.

## Milestones and acceptance

### M1: Standard S3 firmware through Lite

Use the proven engine flash boot through the public bw-board factory and
Lite's loader. Preserve addressed-ELF loading as a distinct mode. Admit a
versioned flash bundle with target identity, flash capacity, merged image or
segments with explicit offsets, ROM identity, SDK/build provenance and optional
debug ELF. Validate chip type, bounds, overlaps and image role; an application
binary and a merged flash image are different inputs.

Fetch/cache approved ROM assets by immutable identity and checksum. Keep
Espressif attribution separate from LabWired's MIT engine license. Rebuild
the same boot state on reset. Select UART0 for the physical 4848 profile.

Acceptance:

1. Existing bare S3 ELF breakpoint/resume behavior remains correct.
2. Both retained real-flash fixtures reach their success markers through the
   public factory and then through the Lite browser route.
3. Reset reproduces the same boot outcome and serial remains readable.
4. Wrong-chip input, missing ROM, truncated/overlapping segments and app-only
   binaries without placement metadata fail with specific messages.
5. Engine-unavailable builds keep a truthful unavailable state.

### M2: 4848S040 RGB display

Implement functional RGB scanout from the guest's actual LCD_CAM/GDMA/PSRAM
state and ST7701 initialization. Schedule required frame events and interrupts;
batch scanout for browser performance while documenting the timing model.
Avoid simulating every pixel edge as a JavaScript circuit event.

The first acceptance guest is independently authored Xtensa machine code that
initializes the actual command path, programs DMA and reads GT911 over I2C.
Its code, descriptors and reused RGB row buffers stay within documented SRAM1.
A follow-up compatibility gate should use retained ESP-IDF/Arduino board firmware
that draws solid colors,
bars, distinct corner markers and asymmetric pixels. Assert framebuffer
dimensions, byte order, stride, coordinates, rotation and frame updates.
Exercise both internal-RAM and PSRAM buffers where supported, descriptor wrap,
reset, backlight and double-buffer handoff. An incorrect pin/bus/format mutation
must fail the relevant visible-result assertion.

### M3: GT911 and interactive GUI

Reuse the existing two-byte I2C register-pointer support but implement GT911
product/configuration reads, ready/count status, contact records, status-clear
acknowledgment and contact injection. Follow the actual board's polling/IRQ
configuration. Support a single contact first with an explicit supported count.

Acceptance: down/move/up produces the expected I2C observations and a guest
redraw; acknowledgement and no-touch states work; corner/rotation mappings are
correct; reset and input recording/replay preserve behavior. Qualify a small
LVGL button/counter workload only after these lower-level checks pass.

### M4: Authoring, build and hardware upload

The sibling audit found no S3 emitter/runtime in `sb3-creator` and no S3 builder
in `stc-compiler`; its Xtensa backend is the ESP8266 LX106 runtime. Lite's Flash
path always generates C and calls `/compile`. The sb3 CLI routes a raw `.bin`
through its STM32 uploader, so passing a new device name is insufficient.
An external-firmware upload needs a distinct S3 route with chip/capacity checks,
explicit offset-zero placement, byte/hash review and post-write verification.
No uploader or compiler has been relabelled to claim S3 support.


Add a versioned S3 runtime/emitter for digital I/O, waits, UART and LEDC,
then display/touch calls. Preserve or explicitly refuse unsupported source
constructs. The existing ESP8266 emitter is a structural example, but its
SDK-free runtime is not Arduino-ESP32.

Build with pinned ESP-IDF or Arduino-ESP32 versions in an appropriate worker
or local toolchain. Return both a debug artifact and flash artifacts with the
builder's offsets; do not reuse classic ESP32 offsets or one target's raw-bin
conventions. A browser upload can use esptool-js/Web Serial where available;
desktop can use esptool through the existing native toolchain boundary.

Acceptance: a generated program compiles, runs in the supported emulation
profile, uploads to an identified physical board and gives the same tested
display/touch result. Record the compiler/runtime identities and firmware
hashes. Physical-board verification is pending access to hardware.

### M5: Supplier adoption and release

Land each behavior in its owning repository and adopt exact supplier commits.
Regenerate the chip/board catalog, pinned package specs/lockfiles, source
mirrors where still applicable, capability tables and notices. Keep functional
compatibility and measured throughput separate. A selected target or passing
CPU loop does not promote display/touch/flash support.

Initial release claims should name the qualified firmware/runtime versions.
Wi-Fi/BLE stacks, encrypted firmware, secure boot, deep sleep, every optional
relay/audio/SD variant and arbitrary application compatibility need their own
evidence before promotion.

## Alternatives

Espressif QEMU supports S3 and is useful as an independent CPU/boot reference.
Its documented graphics option uses a virtual framebuffer that does not exist
in the physical S3, so it does not supply the missing 4848S040 RGB/touch model.
The demonstrated LabWired path avoids replacing the engine and its existing
debugger/circuit contracts.

## Coordination

Lite's `LANES.md` and `lanes/PROTOCOL.md` require a canonical merged claim
before implementation; `docs/VENDORING-REGIME.md` requires upstream-first
changes and exact pin adoption. M1 and the engine/part/UI supplier scopes have
merged claims. The additional Lite empty-project, historical-pin policy and
S040 binding scopes were merged in PR1618 before their implementation. The
owner explicitly approved necessary direct pushes or merges on 2026-11-01;
the earlier approval block is resolved. Source review and qualification remain
required before promotion. New source-emitter, compiler and flasher work still
needs its own coordinated scope.

Current production pins are not promoted merely because a provisional test
passed. No S040 engine release, Lite deployment, new compiler service deployment
or physical-board flash has been performed by this lane.

## Reproducing the M1 review candidate

Use the exact candidate pins and the repository's prescribed dependency workflow.
After dependency verification, the retained engine and flash inputs come from the
installed supplier manifest; no application compiler service is involved:

```sh
node node_modules/bw-board/scripts/fetch-esp32s3-firmware-fixtures.mjs --out artifacts/esp32s3/m1-inputs
npm run sync:labwiredwasm
npm run sync:esp32s3roms
npm run build:gui
BW_ALLOW_LOCAL_BROWSER_PROOF=1 npm run verify:esp32s3-firmware
```

`PROOF_URL` may identify an already served build; the matching local build is
still required for served-byte verification. Otherwise the browser script
serves the built app locally. `BW_BROWSER_PATH` is an explicitly reported
provisional override, never a replacement for the hosted pinned-browser gate.
The script requires the retained file sizes and hashes, all guest markers,
fresh output after restart, real loader refusals, and the served engine hashes.
Missing inputs fail rather than being skipped. Consumer CI registration and
fresh-project entry are implemented under the merged extension claim. Current
installed-package verification passes; built-application and hosted qualification
remain required.
