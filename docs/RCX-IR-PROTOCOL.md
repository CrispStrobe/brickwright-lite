# The RCX infrared protocol, and how we are allowed to implement it

The RCX is reachable only over infrared, through a tower. Everything a host
needs to send it a program is a published fact, and this file records those
facts, where they come from, and the licensing position that lets us use them.

It deliberately contains **no code**. Its job is to make writing the code a
transcription exercise rather than a research one, and to make the provenance
of every constant checkable by someone who was not here.

## Why this file exists: the licensing position

`maehw/WebPBrick` is a browser IDE that already does this — Blockly → NQC →
WASM compiler → `.rcx` → IR download over Web Serial **and** WebUSB. It is an
existence proof that the whole path works from a browser, including with
home-built towers.

Its licensing is split, and the split is the whole point:

| WebPBrick module | Licence | What that means for us |
| --- | --- | --- |
| NQC / WebNQC | MPL-2.0 | usable, and we independently reached the same design |
| Blockly | Apache-2.0 | not needed |
| **everything else** — the IDE, BlockNQC, the RCX comms, the image parser | **GPL-3.0** | **cannot ship in our bundle** |

The GPL half cannot be vendored: `scripts/verify-no-gpl-in-build.mjs` blocks
GPL from the build output, and unlike a compiler this cannot be moved to a
server either — infrared has to be driven by the browser that is plugged into
the tower.

**So we write our own, and we do it as an actual clean room.**

The person who wrote this file has read WebPBrick's source. That makes them
unfit to write the implementation, and no amount of care fixes it — so they
do not write it. The roles are split:

  * **Specifier** (tainted): reads whatever is useful, and writes down the
    contract — this file. Facts, rules, invariants, build order. No code.
  * **Implementer** (clean): must NOT read WebPBrick, at all. Works from this
    file and from the public specification cited below, both of which predate
    or are independent of WebPBrick.
  * **Auditor** (the specifier again): reviews the implementation against the
    contract, and is well placed to notice a divergence precisely because
    they know what the other implementation does.

That is the standard arrangement, and it is worth the ceremony because the
alternative is one person insisting they only took the ideas.

None of the facts below are WebPBrick's to own in any case:

  * a wire protocol is an interface, not an expression of one;
  * every fact below is in Kekoa Proudfoot's **RCX Internals**, published in
    1998 — roughly twenty-five years before WebPBrick — and still online at
    <https://www.mralligator.com/rcx/> and
    <http://graphics.stanford.edu/~kekoa/rcx/>;
  * each one is cited to that document, so the derivation is checkable.

What we must not reproduce is their **expression** — file layout, function
decomposition, naming, the shape of their code. We take facts and ideas, not
source.

And WebPBrick stays useful in the way that costs nothing: as an **oracle**.
When our implementation and theirs disagree about what a brick does, theirs is
the one that has been used against real hardware.

## The facts, each with its citation

All quotations are from RCX Internals unless stated.

### Physical layer

> "bits are sent using a 2400 baud, 8 data, odd parity, NRZ format"

A second, faster mode exists in practice — `firmdl3` raises the link to 4800
baud with parity off for firmware download. That is a property of the tools
rather than of the brick, and it is optional; 2400/odd is what always works.

> "The infrared signal is generated by inverting the serial data and modulating
> it with a 38 kHz carrier. Serial zeros generate light, while serial ones do
> not."

Relevant because the tower **echoes** what it sends: infrared is a broadcast
medium and the transmitter sees its own light. A reader that does not discard
its own transmission will parse every command as if the brick had answered it.

### Message framing

> `55 ff 00 Op Op' D0 D0' D1 D1' ... Dn Dn' Ck Ck'`

  * `55 ff 00` — the header. "The header warms up the serial link and
    delineates the start of a new message."
  * `Op` — "a single byte not equal to `55`, `ff`, or `00`. It is followed
    immediately by its complement."
  * every data byte is likewise followed by its complement;
  * `Ck` is the sum of the opcode and the data bytes, modulo 256, followed by
    its complement.

> "RCX completely ignores messages that have invalid packet checksums"

so a mistake here fails silently rather than loudly, which is the worst
failure mode and the reason to get it right by construction.

### The reply

> "PC sends query opcode … RCX reply opcode is always `~query opcode`"

A reply is identified by carrying the complement of what was asked. This is
also how a real reply is told apart from the tower's own echo.

### The toggle bit — the detail that is easy to miss

> "Messages sent by PC seem to alternate between having `0x08` set and not set.
> This `0x08` bit is a sequence bit only in one special case: RCX never
> executes same exact opcode twice in a row."

Bit 3 of the opcode alternates on every command. Without it, two identical
commands in a row — perfectly reasonable, e.g. the same motor command twice —
collapse into one, and the brick appears to have missed the second. Nothing
errors; the robot just does the wrong thing.

### Arity is encoded in the opcode

> "Paul Haas was right about messages being grouped and parsed by lower 3 bits"

The low three bits of an opcode give its parameter count, so the framing is
self-describing and a parser needs no table to know where a message ends.
Download-continuation and remote commands are the exceptions: they are
variable length.

### A `.rcx` file is a container, not a payload

The image cannot be handed to the brick whole. It carries a count of chunks,
each a task or a subroutine, and each is downloaded separately after the
target program slot has been selected and the previous contents cleared. Our
own compiled output confirms the container shape: an image begins with the
ASCII magic `RCXI`, and a minimal program is 61 bytes with the task name in
the tail.

RCX Internals does **not** describe this container — it is an NQC artefact,
not a brick artefact — so the layout below was measured, not cited. It comes
from the implementer, reading the fixtures in `test/fixtures/rcx-images/`
(each `.rcx` paired with the `.nqc` it was compiled from), and the auditor
reproduced it independently with a second parser that accounts for every byte
of all five images:

```
offset  size  field
0       4     "RCXI"
4       2     version (0x0102)
6       2     chunk count
8       2     symbol count
10      2     target (0x0003 for -TRCX2)
12      ..    chunks, each padded to a 4-byte boundary:
              u8 type, u8 number, u16 length, data
              ... the padding is applied after the LAST chunk too ...
              then symbols, packed WITHOUT alignment:
              u8 type, u8 index, u16 nameLen, name (the NUL is counted)
```

All multi-byte fields are little-endian.

The download order is: select program slot → stop running tasks → delete
tasks and subroutines → begin task download → send blocks.

### The opcode table — read it from the source, do not take it from here

This file deliberately does **not** transcribe the opcode table. The
specifier tried, and produced at least one wrong row within minutes: RCX
Internals lists `Set program number` as `66/6e` with the **R** column set and
`void` arguments, which cannot be a PC-to-brick command with a program number
in it. The table has `P` / `R` / `C` columns (roughly: sent by the PC, sent by
the RCX as a reply, usable from within a program) and reading a row without
reading those columns produces confident nonsense.

So the implementer reads the table from RCX Internals directly, and while
doing so should:

  * treat the `NN/MM` pairs as *the same opcode with the toggle bit clear and
    set* — `10/18`, `50/58`, `70/78`. This is the `0x08` rule above, written
    into the table, and is a useful cross-check that a framing implementation
    is correct;
  * check every opcode against the arity rule — `opcode & 0x07` must equal the
    number of parameter **bytes** in the Encoding column, where a `short` is
    two. `23/2b Play tone / short frequency, byte duration` is three bytes and
    `0x23 & 7 == 3`, which agrees. A row that does not agree has been misread,
    or is one of the documented variable-length exceptions;
  * take the `P` column seriously: only those are commands a host may send.

### The USB tower

The LEGO USB IR tower enumerates as VID `0x0694` / PID `0x0001`. That pair is
a fact about the hardware and is what a WebUSB filter has to match; the serial
tower is an ordinary COM port and needs no such filter.

### Firmware

The standard firmware must already be on the brick for NQC output to run at
all; see `docs/RCX-FIRMWARE.md` for why that file cannot be shipped and what
the free alternatives do instead.

## What to build, and in what order

1. **Framing and checksum**, with the toggle bit — pure functions, testable
   with no hardware at all, against the byte sequences above.
2. **Echo suppression and reply matching** — a reply carries `~opcode`; the
   echo carries the opcode. Testable against a recorded transcript.
3. **`.rcx` container parsing** into chunks. Testable against images our own
   compiler produces, which we already generate in tests.
4. **Web Serial transport** — 2400 baud, odd parity. The simpler of the two.
5. **WebUSB transport** — the USB tower needs endpoint handling; WebPBrick's
   USB path is more than twice the size of its serial path, which is a fair
   estimate of the difference in difficulty.

Steps 1–3 need no brick and no tower, and are where the protocol mistakes
live. They should be finished and tested before any hardware is involved.

## Afterwards: what this file got wrong

The implementation is at `overlay/scratch-gui/src/lib/rcx/rcx-protocol.js`,
with 48 tests in `test/rcx-protocol.test.mjs`. It was written by an agent that
had not read WebPBrick, from this file and from RCX Internals, and then
audited. Three claims above did not survive contact, and are corrected in
place so that the next reader is not misled:

  * **Container alignment.** The first draft of the layout had chunks packed
    tight and the symbol table 4-byte aligned. Both are backwards: chunks are
    padded to four bytes — *including the last one* — and the symbols that
    follow are packed with no alignment at all. Nothing in the two-chunk
    fixtures distinguishes these; `d.rcx`, with five chunks and two variable
    symbols, does.
  * **Endianness was never stated.** It is little-endian throughout. An
    unstated invariant is the same defect as a wrong one.
  * **Replies do not obey the arity rule.** The rule in *Arity is encoded in
    the opcode* above is a fact about **requests** — about the `P` column —
    and does not extend to replies. `0xd2 & 7 == 2`, but its reply carries a
    single error byte. So reply payload lengths are tabulated, not computed,
    and a "simplification" that computes them would break the download path
    quietly.

The audit also found the clean room was not, strictly, necessary for the
framing layer: `rcx_comm.c` — Proudfoot's own reference implementation, the
one `firmdl` is built on — is **MPL-licensed**, not GPL, and could have been
read and shipped. That was discovered after the fact. The clean-room route was
kept anyway, because two independent implementations that agree on the wire
bytes are worth more than one, and `rcx_comm.c` is now available as a third
oracle alongside WebPBrick and brickEmu.
