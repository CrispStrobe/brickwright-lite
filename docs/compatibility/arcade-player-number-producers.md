# Player Number producer boundary

This slice connects an actual multiplayer controller-event parameter to the
primitive inspection producer graph. It adds no block word, reference class,
callable signature or general SDK return-type rule.

## Selected SDK contract

The selected Arcade 4.2.1 bundle's multiplayer `player.ts` creates four Player
instances. Controller-event registration captures each actual Player and passes
it to the current handler. `PlayerProperty.Number` is 2; the original getter
returns the Player's index plus one. The public `getPlayerProperty` returns 0
for a missing Player. The pinned [multiplayer source](https://github.com/microsoft/pxt-arcade/blob/2d7d59b5226e8a1a1e05e8042dd9f5248ed68fea/libs/multiplayer/player.ts)
provides the public reference. Qualification binds the actual selected bytes.
Existing Microsoft MIT notices remain applicable.

## Source evidence

An unchanged lexical `mp.onControllerEvent`, fixed `ControllerEvent.Connected`
or `.Disconnected`, and its actual one-parameter function establish the Player
producer. An annotation alone establishes nothing. Existing directed edges carry
that producer through local aliases, actual ordinary function arguments and
returns, while checking every writer.

Only an unchanged `mp.getPlayerProperty` with the direct fixed selector
`mp.PlayerProperty.Number` derives Number. A safe lookup may include actual Null
or Undefined writers, but still needs a concrete event-Player producer. Other
reference, String, Number or unknown alternatives refuse. This is not a change
to nullable callable signatures or an admission of other Player factories.

Reference annotations remain opaque to primitive inspection. A compatible
`mp.Player` constraint can accompany an actual Player producer through the safe
lookup; it cannot create that producer or authorize inspecting the reference.
Incompatible declared parameter or variable constraints refuse.

Namespace/member replacement, computed namespace access, escaped registration,
getter or enum receivers, private multiplayer state access, and Player prototype
exposure refuse. Potential writes to the selected Player identity/getter fields
also refuse, including through aliases. Unknown computed writes require a proved
non-string primitive key. This conservative barrier can refuse unrelated writes
with the same sensitive field names; it does not reconstruct arbitrary object
metaprogramming or custom Player implementations.
