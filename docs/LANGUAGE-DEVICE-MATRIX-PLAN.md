# Language x device matrix — one truth, shown to users, closed cell by cell

Status: **active plan, lane open**. Created 2026-09-05 by session `lego-ac`
(`Claude-Session: https://claude.ai/code/session_01L3xy8YZKHGfHAkysBEREXG`).
Owner of record for the truth lane (T1, T2) and the ASM reader (L1): lego-ac.
Every other task is unclaimed until a row in `LANES.md` says otherwise.

The product question this answers: *write in any language the Code tab offers,
run it on any chip the Circuit Designer or the device picker offers, in the
simulator and on real silicon.* Today that is partly true, partly false, and
nowhere written down in a form the GUI and the docs both read. This plan makes
one table the source of truth, shows it to the user, derives the docs from it,
and then lists what closes each cell that is still open.

## 1. Decisions (made — do not re-litigate in tasks)

### D1. A cell has two halves, and each half is a fact, not a verdict

For a language **L** and a device **D**, the cell records:

- **native** — L itself runs on D. The artefact is L's own program (a `.py`
  for MicroPython, a `.bas` typed into a BASIC ROM, a `.hex` from a C or ASM
  toolchain). Sub-facts: which toolchain, where it runs (`local` in the
  browser, `hosted` on stc-compiler, or `none` because the chip runs the
  language directly), and whether that artefact reaches the simulator, real
  silicon, or both.
- **lowered** — L is read into the dialect AST and re-emitted as something D
  runs natively. The learner's text does not run; its meaning does. Sub-facts:
  the reader used, the emitter used, and the native cell it lands in.

A cell is therefore one of **native**, **lowered**, or **both**. There is no
"refused" cell. Where a native half is physically impossible, the cell says
`native: null` **with a reason** (`ram`, `flash`, `no-port`, `no-emulator`,
`licence`) and the lowered half carries the load. "Physically impossible" is a
strong claim and every use of it in the table cites the number it rests on.

### D2. The table is data in the code, gated against the code

`overlay/scratch-gui/src/lib/bw-matrix/capabilities.js` is a frozen, versioned
data module. It is hand-authored — some facts (the hosted service's target
list) do not live in this repository — but every fact that *does* live here is
cross-checked by a test that reads the real source:

| fact in the table | checked against |
| --- | --- |
| device ids, groups, `compile`, `emulator` | `DEVICE_GROUPS` in `pseudocode-importer.jsx` |
| silicon transport per device | `flashFamily()` and the `flasher.js` exports |
| local vs hosted assembler | `LOCAL_ASM_TARGETS` in `bw-asm/assemble-route.js` |
| local vs hosted C compiler | `LOCAL_TARGETS` in `sdcc-wasm/compiler.js` and `smallerc-wasm/compiler.js` |
| which cores `generateC` emits for | the `_core` selection in `sb3-creator.js` |
| which languages have a reader | the `sb3-creator-*.js` reader modules |
| hosted compile/assemble targets | `docs/generated/hosted-targets.json`, regenerated by `scripts/gen-hosted-targets.mjs` from a stc-compiler checkout (pinned at `79df4b6d`; the derived facts matched the hand read exactly, so the snapshot was accurate) |

A table row that the source contradicts fails the build by name. A table row
that nothing checks is marked `evidence: 'declared'` and rendered with that
label — the reader can see which facts are proven and which are only stated.

### D3. GUI and docs are both derived, never hand-maintained

Two GUI surfaces and one document read the same module:

- **Overall matrix** — a "What runs where?" view reachable from the Code tab's
  device dropdown: languages down, devices across, each cell native/lowered/
  both, with sim and silicon marks.
- **Contextual badge** — beside ▶ Run and ⬇ Deploy, for the *chosen* language
  and device: `native · sim + silicon`, `lowered via C · sim only`, or the
  reason nothing is available. The buttons' enabled state comes from the same
  lookup, so the badge cannot say one thing and the button do another.
- **`docs/generated/LANGUAGE-DEVICE-MATRIX.md`** — generated by
  `scripts/gen-language-device-matrix.mjs`, with `--check` wired into the build
  like the other generators. `docs/CHOOSING-HARDWARE.md` and
  `docs/device-matrix.md` link to it instead of carrying their own tables.

### D4. Native closures are preferred where a permissive runtime exists

Where a chip can run a language natively with a permissively licensed runtime,
we add the native half even though the lowered half already works, because a
learner who wrote Python and sees Python on the board learns something the
lowered path hides. Licences that qualify: MIT, BSD, Apache-2.0, zlib,
MPL-2.0 (file-level). GPL toolchains stay hosted, as they are today.

### D5. Peripheral verbs are a second table, joined to this one

Which parts a program can drive (`lcd print`, `oled pixel`, `set servo`) is
per part × per family, not per language × device, and is owned by the
part-profile lane (§3, Lane P). The matrix cell links to it: a lowered cell
that lands in C on the 8051 inherits the 8051 C driver set. The two tables
are joined by family id and nothing else.
